# Android-шлюз SMS (SP10-01)

Телефон с SIM сам опрашивает сервер: ему не нужен входящий доступ, достаточно исходящего HTTPS. Сервер сообщения не отправляет.
Контракт маршрутов: `docs/sms-gateway-openapi.yaml`. Тесты T-13: `SmsGatewayServiceTest` (имитатор устройства на настоящей базе).
Результат на реальном аппарате и полевой прогон по трём сетям это SP10-02 (QA), здесь только серверная часть и протокол.

## Правда о статусе SMS (главное правило)
| Статус | Когда ставится | Кто ставит |
|---|---|---|
| `QUEUED` | сообщение лежит в очереди (или закреплено за устройством, но не подтверждено) | сервер |
| `SUBMITTED` | устройство подтвердило, что приняло сообщение к отправке (`ACCEPTED`) | событие устройства |
| `SENT` | устройство сообщило, что SMS ушло в сеть оператора (`SENT`) | событие устройства |
| `DELIVERED` | устройство получило от сети отчёт о доставке и прислало `DELIVERED` | событие устройства |
| `FAILED` | устройство сообщило отказ, срок сообщения вышел или пять аренд подряд без подтверждения | устройство или сервер |
| `UNKNOWN` | устройство приняло сообщение, но отчётов нет дольше срока (по умолчанию 15 минут) | сервер |

Опрос (`poll`) статус сообщения не меняет никогда: ни первый, ни повторный, ни поздний, ни пустой. HTTP 200 на опрос или на событие тоже не доказывает ничего про телефон получателя.
`DELIVERED` и `SENT` возможны только у сообщения, которое подтвердило то же устройство. База дополнительно держит это ограничением (`sms_sent_delivered_need_device`).
Повторное событие безопасно (`IGNORED`), статус не откатывается назад. Противоречие («доставлено» после `FAILED` и наоборот) отклоняется (`REJECTED`).
Если устройство молчит, статус `UNKNOWN`: сервер не гадает. Настоящий поздний отчёт самого устройства `UNKNOWN` снимает.

## Протокол устройства
Авторизация: `Authorization: Bearer <токен устройства>` на каждом запросе. Токен только на телефоне, на сервере хеш.

1. **Опрос.** `POST /api/v1/gateway/poll` с телом `{"limit": 20}` (необязательно, максимум 50). Ответ: `{"messages":[{"commandId","phone","body"}]}`.
   Сообщения закрепляются за устройством на 60 секунд. Повторный опрос того же устройства вернёт те же сообщения (срок не продлевается), другим устройствам они не отдаются.
2. **Подтверждение.** Сразу после того как приложение сохранило сообщение у себя, оно шлёт событие `ACCEPTED`. Без него через 60 секунд сообщение вернётся в очередь (до пяти раз, потом `FAILED`).
3. **Отчёты.** `POST /api/v1/gateway/events` с телом `{"events":[{"commandId","type","reason"}]}`, до 100 за раз. Типы: `ACCEPTED`, `SENT` (по результату `SmsManager`), `DELIVERED` (по отчёту доставки), `FAILED` (поле `reason`: короткий код A-Z 0-9 _, не текст).
   Ответ: `{"results":[{"commandId","outcome"}]}` где outcome это `APPLIED`, `IGNORED` или `REJECTED`. Любой из трёх значит «сервер ответил по этому событию»: его можно убрать из очереди отправки.

Что обязано делать приложение (иначе правда о статусе нарушится):
- **Дедупликация по `commandId`.** Приложение хранит принятые `commandId` на диске (переживает перезапуск). Повторно выданное сообщение с уже известным `commandId` второй раз не отправляется, а только повторяется событие `ACCEPTED`.
  Сервер даёт гарантию «не менее одного раза», защита от двойной SMS лежит на устройстве.
- **События не терять.** События пишутся в локальную очередь и повторяются, пока не придёт ответ сервера. Порядок для одного сообщения: `ACCEPTED`, `SENT`, `DELIVERED` или `FAILED`.
- **`DELIVERED` только по отчёту сети.** Не по успешному вызову `SmsManager`, не по таймеру, не по ответу сервера.
- Опрашивать не реже чем раз в 10-15 секунд, пока есть связь. Тишина дольше срока это сигнал для алерта «молчание шлюза» (SP13-03).
- Текст SMS (в нём код) нигде не логировать и не оставлять в истории после отправки.

## Настройка
1. Токен и хеш: `java tools/GatewayDeviceKey.java pixel-1` из папки `backend`. Токен вводится в приложение на телефоне, хеш идёт на сервер.
2. На сервере (все переменные нужны вместе, иначе приложение не стартует):
   ```
   export JOLOMO_SMS_GATEWAY=android
   export JOLOMO_SMS_DISPATCHER_ENABLED=false
   export SMS_GATEWAY_DEVICES="pixel-1:<хеш>"          # несколько через запятую
   ```
   Необязательно: `SMS_GATEWAY_LEASE_SECONDS` (60) и `SMS_GATEWAY_UNKNOWN_AFTER_MINUTES` (15).
3. Только TLS: токен и телефоны в запросах нельзя пускать по http. Обратный прокси отдаёт только https.
4. Отзыв устройства: убрать его из `SMS_GATEWAY_DEVICES` и перезапустить сервер. Потерянный телефон отзывается сразу так же.

В режиме `fake` (по умолчанию) маршрутов `/api/v1/gateway/*` нет вообще.

## Что учесть дальше
- Алерт «молчание шлюза» (SP13-03) читает `SmsGatewayService.lastSeenAny()`; сообщения, застрявшие в `QUEUED`, видно по таблице `sms_messages`.
- Устройство одно, поэтому один сбой телефона останавливает все SMS (OTP на вход и коды доставки). Решение про запасное устройство (второй телефон в `SMS_GATEWAY_DEVICES`) за владельцем.
- Статусы SMS не влияют на статусы посылок и броней: доставка посылки подтверждается только кодом получателя, а не отчётом SMS.
