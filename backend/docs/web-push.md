# Web Push (SP11-02)

Web Push необязателен и никогда не доказательство. Он не подтверждает ни бронь, ни доставку: решения принимает только сервер по событиям и кодам. Приложение работает полностью одинаково с push и без него.

## Что делает сервер
- **Opt-in.** Человек разрешил уведомления в браузере, приложение отправляет `PushSubscription.toJSON()` на `POST /api/v1/me/push-subscriptions`. Повтор с тем же адресом безопасен и продлевает срок.
- **Отказ в разрешении** это обычное состояние. Тогда приложение маршрут не вызывает, подписки нет, ошибок нет. Если сервер вообще не настроен на push, `GET /api/v1/push/vapid-key` отвечает 503 `PUSH_DISABLED`, и приложение не предлагает включить уведомления.
- **Отписка.** `DELETE /api/v1/me/push-subscriptions/{id}` или `POST /api/v1/me/push-subscriptions/revoke` с адресом (браузер знает адрес, а не id). Работает всегда, даже если сервер сейчас не настроен. Повтор безопасен.
- **Сбой.** Отправка идёт после фиксации деловой транзакции и ничего не пишет в деловые данные. `PushNotifier.notifyUser` не бросает исключений: сбой push остаётся тихим и не подтверждает и не отменяет никакое действие.

## Что хранится
Таблица `web_push_subscriptions`: адрес (endpoint), срок, отзыв (причина `USER`, `GONE`, `REPEATED_FAILURES`, `POLICY`), счётчик сбоев. Ключи шифрования подписки не хранятся. Адрес подписки работает как токен для пробуждения устройства: в ответах API и журналах его нет. Сроки хранения для строк подписок ждут юриста, как и для остальных данных; удаляются они вместе с синтетическим пользователем.

## Полезная нагрузка
Push уходит **пустым**: только заголовки VAPID, TTL 3600 и Urgency normal. В нём не может быть контактов, текста, кода доставки. Service worker по такому push показывает общее «в JolOmo есть новое» и открывает приложение, которое само запрашивает данные под сессией человека. Шифрованную нагрузку (RFC 8291) можно добавить позже отдельной задачей, если появится требование показывать текст.

## Защита от SSRF
Адрес подписки приходит от клиента. Сервер принимает и вызывает только `https` на стандартном порту, без логина в адресе и только на доменах известных push-служб (`fcm.googleapis.com`, `push.services.mozilla.com`, `push.apple.com`, `notify.windows.com`, включая поддомены). Список меняется через `PUSH_ALLOWED_HOSTS`. Проверка повторяется при каждой отправке, а редиректы не выполняются. Адрес вне списка при отправке отзывается с причиной `POLICY`.

## Отзыв и лимиты
- 404 и 410 от push-службы: подписка отзывается сразу (`GONE`).
- Любой другой сбой считается; пять подряд (`jolomo.push.max-failures`) отзывают подписку (`REPEATED_FAILURES`), успех обнуляет счётчик.
- Не больше 10 действующих устройств на человека (409 `PUSH_LIMIT_REACHED`).
- Срок подписки 90 дней (`jolomo.push.subscription-days`) или срок от браузера, если он короче. Приложение продлевает его повторным opt-in при запуске.
- Если на устройстве сменили аккаунт, адрес переходит к новому человеку, у прежнего подписка исчезает, и он не может отозвать чужую.

## Настройка
1. Из папки `backend`: `java tools/VapidKeygen.java`. Печатает `PUSH_VAPID_PUBLIC_KEY` и `PUSH_VAPID_PRIVATE_KEY`.
2. В окружение сервера: `PUSH_ENABLED=true`, оба ключа и `PUSH_VAPID_SUBJECT=mailto:адрес-владельца`. Закрытый ключ хранить вместе с остальными ключами в копиях. Смена ключей отключает все текущие подписки.
3. Включено без ключей или с неверным форматом: приложение не стартует.

## Что дальше
Сам вызов `PushNotifier.notifyUser(userId)` готов, но к событиям брони и посылки он пока не подключён: какие события будят человека, решает продукт, и это отдельный небольшой шаг. Для фронтенда: service worker с обработчиком `push`, запрос разрешения только по действию человека, `applicationServerKey` из `GET /api/v1/push/vapid-key`.
