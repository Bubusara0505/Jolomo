# JolOmo — backend

Java 21, Spring Boot (кандидат 4.1.1 по ТЗ), Gradle Kotlin DSL, PostgreSQL 16 + PostGIS, Flyway.

## Запуск
1. `cp .env.example .env`, задайте `DB_PASSWORD`, `OTP_PEPPER` (`openssl rand -hex 32`), `SESSION_SECRET` (`openssl rand -hex 32`) и `SMS_BODY_KEY` (`openssl rand -base64 32`) `ADMIN_TOTP_KEY` (`openssl rand -base64 32`, шифрует секреты TOTP администраторов) и `IDENTITY_KEY` (`openssl rand -base64 32`, ключ файлов личности; потеряете ключ, потеряете файлы). `DELIVERY_OTP_PEPPER` (`openssl rand -hex 32`, секрет кода доставки, не равен `OTP_PEPPER`). Без любого из этих секретов приложение не стартует.
2. `docker compose up -d` — локальная БД с PostGIS.
3. `./gradlew bootRun` (переменные из `.env` экспортируйте в окружение). Чтобы видеть код SMS в логе: `SPRING_PROFILES_ACTIVE=dev SMS_FAKE_LOG_BODY=true ./gradlew bootRun`; без профиля `dev` флаг не даст стартовать.
4. Проверка: `curl localhost:8080/actuator/health`.

## Тесты
`./gradlew test` — нужен запущенный Docker (Testcontainers с образом `postgis/postgis:16-3.4`).
H2 не используется.

## Правила
- Схему меняет только Flyway (`src/main/resources/db/migration`), Hibernate таблицы не создаёт.
- Модули: auth, users, verification, trips, bookings, parcels, courier, admin, sms, events, shared.
  У `courier` нет маршрутов.
- Версии зависимостей зафиксированы здесь и в `build.gradle.kts` (замена FRG-03).

- Версии зависимостей фиксирует `gradle.lockfile`: создать один раз командой `./gradlew dependencies --write-locks`.

## API
Полное описание: `openapi.yaml`. Кратко:

- Ошибка всегда одним конвертом `{"code", "message" (ключ перевода), "correlationId"}`, без трассы стека.
  Заголовок `X-Correlation-Id` принимается и возвращается, id попадает в каждую строку журнала `[cid=...]`.
- `GET /actuator/health`.
- `POST /api/v1/auth/otp/request` `{phone, purpose}` -> 202 `{challengeId, expiresAt, resendAfterSeconds}`.
  Телефон `+996` и 9 цифр. Лимиты: 1 запрос в 60 с и 5 в час на телефон, 30 в минуту на всех (`OTP_BUSY`).
- `POST /api/v1/auth/otp/verify` `{challengeId, phone, purpose, code}` -> 200 `{verified, userId}` и три cookie.
  Ошибки: `OTP_INVALID`, `OTP_EXPIRED`, `OTP_ATTEMPTS_EXHAUSTED`, `USER_SUSPENDED`.
- `POST /api/v1/auth/refresh` -> 204 и новые cookie; `SESSION_INVALID` или `SESSION_REUSED` (401) означают «нужен новый вход».
- `POST /api/v1/auth/logout` -> 204. `GET /api/v1/auth/csrf`. `GET /api/v1/me`.

## Сессии и CSRF (для фронтенда)
- Три cookie: `jl_access` (15 минут) и `jl_refresh` (30 дней, только для `/api/v1/auth`) HttpOnly; Secure; SameSite=Lax,
  а также `jl_csrf`, который читает JS. Токены в `localStorage` не хранить.
- На каждый POST/PUT/PATCH/DELETE, когда есть cookie сессии, добавлять заголовок `X-CSRF-Token` со значением `jl_csrf`
  (иначе 403 `CSRF_INVALID`). Если cookie пропала, вызвать `GET /api/v1/auth/csrf`.
- При 401 `UNAUTHENTICATED` один раз вызвать refresh и повторить запрос. Запросы refresh отправлять строго по одному:
  два параллельных refresh одним токеном считаются кражей и отзывают сессию.
- Реальные SMS не отправляются: фейковый шлюз. Текст SMS хранится в базе зашифрованным (`SMS_BODY_KEY`) и стирается после отправки.

## Администраторы и первый вход
Вход администратора: логин, пароль и TOTP (или одноразовый код восстановления). Сессия отдельная от пользовательской (cookie `jl_admin`, 30 минут).
Права по ролям: `REVIEWER` проверяет заявки, `SUPPORT` принимает инциденты, `OWNER` может всё и один управляет учётными записями.

Создать первого администратора (один раз, на пустой базе):
1. `export ADMIN_TOTP_KEY=$(openssl rand -base64 32)` и `export ADMIN_BOOTSTRAP_LOGIN=owner`, остальные секреты как обычно.
2. Запустить `./gradlew bootRun`. В консоли один раз напечатаются пароль, ключ TOTP и 8 кодов восстановления. Сохраните их в менеджере паролей, ключ TOTP добавьте в приложение-аутентификатор (ввод ключа вручную).
3. Остановить приложение и убрать `ADMIN_BOOTSTRAP_LOGIN` из окружения.
Потеря устройства: другой OWNER вызывает `POST /api/v1/admin/accounts/{id}/reset`. Если OWNER единственный, а коды восстановления потеряны, остаётся удалить его строку в `admin_accounts` и повторить создание.

## Поездки (SP05-01)
- `POST /api/v1/trips` создаёт черновик (нужен профиль водителя). `GET /api/v1/trips/mine` свои поездки.
  `GET /api/v1/trips/{id}`: владельцу своя в любом статусе, остальным только опубликованная в публичном виде (без владельца, телефонов, документов).
- `PATCH /api/v1/trips/{id}` правит поля **или** меняет статус: `{"status":"PUBLISHED"}` публикует, `{"status":"CANCELLED"}` отменяет. Не одновременно.
- Матрица: чужая поездка это 404 (не отличить от несуществующей); публикация и правка опубликованной требуют допуска водителя и загруженного
  выключателя обязательств (иначе 403 `NOT_APPROVED` или `OBLIGATIONS_NOT_LOADED`); отмена доступна владельцу всегда, повтор безопасен;
  завершённая и отменённая поездки заморожены (409 `INVALID_TRIP_STATE`).
- У опубликованной поездки правятся только цена, число мест и слотов посылок (не ниже уже занятого). Маршрут и время зафиксированы: для их смены поездку отменяют и создают новую.
- Поиск `GET /api/v1/trips` (SP05-02), события `domain_events` (SP05-04), Idempotency-Key (бронирование, SP06) в этой задаче не входят.

## Поиск поездок (SP05-02)
`GET /api/v1/trips?direction=BISHKEK_TO_KARAKOL` (вход не нужен). Параметры:
- `direction` обязателен (`BISHKEK_TO_KARAKOL` или `KARAKOL_TO_BISHKEK`);
- `from`, `to` окно отправления в ISO-8601 UTC (по умолчанию `from` = сейчас, `to` не ограничен); поездка подходит, если её окно пересекается с запрошенным;
- `nearPickupLocationId` и `radiusMeters` (по умолчанию 5000, максимум 100000): только поездки, чья точка посадки не дальше радиуса от выбранной точки каталога, ближайшие первыми при равном времени; в ответе `distanceMeters`;
- `seats` (по умолчанию 1) сколько свободных мест нужно; `limit` (по умолчанию 20, максимум 50) и `offset`.
Всегда исключены: черновики, отменённые и завершённые, просроченные (окно отправления закончилось), полные и поездки другого направления.
В ответе только публичные поля: направление, окно, точка (код, названия KY/RU/EN, координаты), свободные места, цена в KGS. Ни владельца, ни телефонов.

План запроса: тест `TripSearchExplainTest` пишет `EXPLAIN (ANALYZE, BUFFERS)` в `backend/build/explain/trip-search.txt`. Запись плана хранится в `backend/docs/explain-trip-search.txt`.

## Журнал событий (SP05-04)
Таблица `domain_events` append-only: триггер базы запрещает UPDATE и DELETE. Событие пишется в той же транзакции, что и изменение поездки
(`TRIP_CREATED`, `TRIP_UPDATED`, `TRIP_PUBLISHED`, `TRIP_CANCELLED`), у каждой сущности версии 1, 2, 3 без дублей и пропусков.
Повтор записи с тем же `event id` игнорируется (`DomainEventStore.append(eventId, ...)` вернёт `false`). Отказанные операции и правки без изменений событий не пишут.
В payload только идентификаторы и значения полей поездки, без телефонов. Журнал не имеет HTTP-маршрутов.

## Брони (SP06)
- `POST /api/v1/trips/{tripId}/bookings` с телом `{"seats":N}` и заголовком `Idempotency-Key` запрашивает места. Запрос места **не занимает** (места занимает принятие водителем).
  Отказы: нет такой, не опубликована или отменена (404 `TRIP_NOT_FOUND`), своя поездка (403 `OWN_TRIP`), уже отправилась (409 `TRIP_DEPARTED`), мест меньше запрошенного
  (409 `NOT_ENOUGH_SEATS`), уже есть активный запрос на эту поездку (409 `BOOKING_ALREADY_ACTIVE`, держит и частичный индекс базы), `seats` не больше 0 (400 `INVALID_SEATS`).
- `POST /api/v1/bookings/{id}/accept`, `/reject`, `/cancel`; `GET /api/v1/bookings/mine`, `GET /api/v1/bookings/{id}`, `GET /api/v1/trips/{tripId}/bookings` (водителю).
- Последнее место: принятие идёт под `SELECT ... FOR UPDATE` строки поездки, затем строки брони (порядок блокировок везде один). Побеждает один, остальные получают 409 `NO_SEATS_LEFT`.
  Отмена возвращает места только при переходе ACCEPTED -> CANCELLED, то есть не более одного раза. Повторные accept, reject и cancel безопасны и места не трогают.
- Права: принимает владелец поездки с допуском (правило `MANAGE_BOOKINGS`, данные в `eligibility_rules`). Отклонять и отменять можно и без допуска.
  Пассажир отменяет свой запрос или принятую бронь, водитель только принятую. После отправления отмены и принятия нет. Чужая бронь это 404 `BOOKING_NOT_FOUND`.
- Если водитель отменяет поездку, все её REQUESTED и ACCEPTED брони в той же транзакции становятся CANCELLED (`cancelled_by = TRIP_CANCELLED`), места не возвращаются.
- Идемпотентность: запись о ключе (`idempotency_records`) пишется в той же транзакции, что и бронь. Тот же ключ и то же тело возвращают сохранённый ответ (заголовок `Idempotent-Replayed: true`),
  другое тело с тем же ключом это 409 `IDEMPOTENCY_KEY_REUSED`. Отказы не сохраняются. Параллельные одинаковые запросы создают одну бронь. Сроки хранения записей не заданы (ждут юриста), удаления пока нет.
- События: `BOOKING_REQUESTED`, `BOOKING_ACCEPTED`, `BOOKING_REJECTED`, `BOOKING_CANCELLED` в `domain_events` (aggregate `BOOKING`), без телефонов.
- Контактов в ответах нет вообще: их откроет SP07-01 после ACCEPTED. `COMPLETED`, `NO_SHOW` и `REVIEW_REQUIRED` ставит SP07-03.

## Контакты по брони (SP07-01)
- `GET /api/v1/bookings/{id}/contact` единственный маршрут, который отдаёт телефон по броне. Остальные ответы по броням (создание, списки, просмотр, повтор по Idempotency-Key, события) телефонов не содержат вообще.
- Не участник брони: 404 `BOOKING_NOT_FOUND`. Участник, но бронь не `ACCEPTED` (запрос, отказ, отмена, отмена поездки): 403 `CONTACT_NOT_AVAILABLE`, в ответе ничьих данных нет.
- `ACCEPTED`: пассажиру приходит телефон водителя (`role: DRIVER`), водителю телефон пассажира (`role: PASSENGER`), больше ничего. Ответ с `Cache-Control: no-store`.
- После отмены контакт снова закрыт. Что с контактами после `COMPLETED` и `NO_SHOW`, решит SP07-03 (пока закрыты). Телефон в журнал не пишется; аудита просмотров контакта пока нет (ТЗ его не требует).

## Посылки: создание (SP07-04)
- `POST /api/v1/parcels` (`tripId`, `size` S/M/L, `category`, `recipientPhone`) с `Idempotency-Key`. Маршруты чтения: `GET /api/v1/parcels/mine`, `GET /api/v1/parcels/{id}` (отправитель или назначенный водитель), `GET /api/v1/trips/{tripId}/parcels` (водителю).
- **Запрет по умолчанию.** Пока на сервере не загружен набор обязательств `PARCEL_CREATE` (отдельный от `TRIP_PUBLISH`), любое создание отклонено: 403 `OBLIGATIONS_NOT_LOADED`. HTTP-маршрута, который его включает, нет. В заявке сохраняется версия набора, действовавшего при создании (`obligation_version`).
- Проверки: поездка существует, опубликована, не своя, не отправилась, у неё есть свободный слот посылки (404 `TRIP_NOT_FOUND`, 403 `OWN_TRIP`, 409 `TRIP_DEPARTED`, 409 `NO_PARCEL_CAPACITY`); размер (400 `INVALID_PARCEL_SIZE`); категория из таблицы `parcel_categories` (400 `INVALID_PARCEL_CATEGORY`);
  телефон получателя `+996` и 9 цифр (400 `INVALID_RECIPIENT_PHONE`); получатель не отправитель и не водитель (400 `RECIPIENT_IS_SENDER`, `RECIPIENT_IS_DRIVER`), иначе код доставки мог бы подтвердить свой же человек.
- Создание **слот не закрепляет**: слот займёт принятие водителем (SP08-01). Цены посылки в модели нет (согласуется вне платформы).
- **Категории это данные.** В `parcel_categories` лежат рабочие заготовки `DOCUMENTS` и `SMALL_GOODS`, это не решение юриста. Подписанный перечень (LEG-07/08) заменяет строки таблицы без выпуска кода.
- Телефон получателя лежит только в `parcel_requests.recipient_phone`; в ответах, событиях (`PARCEL_REQUESTED`, `PARCEL_CANCELLED`) и журнале его нет.
- Если водитель отменяет поездку, заявки в состоянии REQUESTED и ACCEPTED становятся CANCELLED в той же транзакции.

## Посылки: слот и решения водителя (SP08-01)
- `POST /api/v1/parcels/{id}/accept`, `/reject`, `/cancel`. Принятие закрепляет **один слот посылки** (размер S, M, L слот не меняет), под блокировкой строки поездки `FOR UPDATE`, затем строки заявки, тот же порядок, что у мест.
  У последнего слота один победитель, остальные получают 409 `NO_PARCEL_CAPACITY` (тест T-02 на PostGIS: 8 потоков на один слот).
- Принятие требует допуска водителя (правило `MANAGE_PARCELS` в `eligibility_rules`) **и** загруженного набора обязательств `PARCEL_CREATE` (default deny: если юрист выключил набор, новые принятия закрыты; отказ и отмена работают всегда).
- Отмена: отправитель отменяет заявку или принятую посылку, водитель только принятую. Слот возвращается один раз, при переходе ACCEPTED -> CANCELLED; повторная отмена ничего не меняет.
  Когда посылка уже у водителя (PICKUP_CONFIRMED и дальше), отмены нет (409 `INVALID_PARCEL_STATE`), дальше custody (SP08-02) и разбор. После отправления поездки принять или отменить нельзя (409 `TRIP_DEPARTED`).
- Повторные accept, reject и cancel безопасны. Чужая заявка это 404 `PARCEL_NOT_FOUND`. События: `PARCEL_ACCEPTED`, `PARCEL_REJECTED`, `PARCEL_CANCELLED`, без телефонов.
- Правка слотов опубликованной поездки ниже числа принятых посылок отклоняется (`CAPACITY_BELOW_TAKEN`).

## Посылки: custody (SP08-02)
- `POST /api/v1/parcels/{id}/pickup` (ACCEPTED -> PICKUP_CONFIRMED), `/dispatch` (-> IN_TRANSIT), `/arrive` (-> DELIVERY_PENDING). Названия `pickup` и `dispatch` из ТЗ 1.7, `arrive` для третьего шага выбран мной, в ТЗ у него маршрута нет.
- Переход делает только назначенный (владелец поездки) проверенный (правило `MANAGE_PARCELS`) водитель, строго по цепочке и по одному шагу. Все остальные получают 404 `PARCEL_NOT_FOUND`, пропуск шага или движение назад это 409 `INVALID_PARCEL_STATE`, неодобренный водитель это 403 `NOT_APPROVED`.
- Свидетельство custody: каждый переход пишет строку `audit_events` (кто, когда, из какого состояния в какое, причина `CUSTODY_TRANSITION`, действие `PARCEL_PICKUP_CONFIRMED`, `PARCEL_IN_TRANSIT`, `PARCEL_DELIVERY_PENDING`) и событие `domain_events` в той же транзакции. Повтор уже сделанного шага безопасен и новых строк не пишет.
- Забрать посылку (`pickup`) можно, пока поездка опубликована. Дальнейшие шаги фиксируют физический факт и от статуса поездки не зависят, а также не требуют набора обязательств: посылку нельзя стопорить на полпути.
- Если посылка уже у водителя, её нельзя отменить ни отправителю, ни водителю, и отмена поездки её молча не снимает (она остаётся для разбора). Незабранные принятые заявки отмена поездки снимает.
- `DELIVERED` из этой цепочки недостижим: его даст только код получателя (SP09-02). Строки `audit_events` пока не защищены от правки на уровне базы (запрет UPDATE/DELETE можно добавить отдельной миграцией, как у `domain_events`).


## Код доставки (SP09-02, SP09-03)
Доставку подтверждает только получатель без аккаунта. Когда водитель на месте (`DELIVERY_PENDING`), он вызывает
`POST /api/v1/parcels/{id}/delivery-challenge`: сервер создаёт код и отправляет SMS на номер получателя из заявки со ссылкой
`DELIVERY_LINK_BASE/{challengeId}`. Страница получателя (SP10-03) вызывает `GET /api/v1/deliveries/{challengeId}` и
`POST /api/v1/deliveries/{challengeId}/verify` `{code}` без входа и без CSRF-заголовка.
- Код привязан к посылке, номеру получателя и переходу `DELIVERY_PENDING -> DELIVERED` (HMAC с `DELIVERY_OTP_PEPPER`), хранится как хеш, потребляется один раз. Кода нет в ответах, журнале и событиях; в базе он лежит только внутри зашифрованного текста SMS до отправки.
- Три ошибки подряд: проверка заблокирована, посылка получает `VERIFICATION_LOCKED` (`423 DELIVERY_LOCKED`). Спор (`DISPUTED`) отсюда не открывается никогда.
- Снять блокировку может только поддержка (`POST /api/v1/admin/parcels/{id}/unlock-verification`, право `INCIDENT_RECORD`, код причины, аудит). Это возвращает посылку в `DELIVERY_PENDING`, но доставленной не делает: нужен новый код от водителя.
- Не чаще одного кода в 60 секунд и не более 5 в час на посылку. Код живёт 2 часа.
- Текст SMS пока только на русском (каталоги KY/RU/EN в SP11-03).

## Инциденты поддержки (SP09-01)
`POST /api/v1/admin/incidents` `{parcelId, kind, reasonCode}` (право `INCIDENT_RECORD`: SUPPORT и OWNER). Инцидент это запись, а не действие:
статус посылки, слоты и коды не меняются, `DELIVERED` и `DISPUTED` отсюда поставить нельзя. В записи сохраняются состояние посылки и версия условий
(`obligation_version` посылки). Свободного текста нет, поэтому персональных данных в инциденте не бывает. Виды инцидентов лежат в таблице
`incident_kinds` (рабочая заготовка, подписанный перечень юриста заменит строки). Записи инцидентов и строки аудита только дописываются (триггеры базы).
**`DISPUTED` пока никто не ставит:** по ТЗ это «разобранное решение», шаг решения ещё не определён продуктом и юристом.

## Ровно одна доставка (SP10-04)
Потребление кода, статус `DELIVERED`, аудит и событие пишутся одной транзакцией: сбой посередине откатывает всё, повтор доводит доставку ровно один раз
(тест `DeliveryAtomicityTest` имитирует отказ на последнем шаге). База добавляет свои гарантии: у посылки не бывает второго события `PARCEL_DELIVERED`
и второго потреблённого кода. Если ответ получателю потерялся уже после фиксации, повторная отправка того же кода даёт `409 DELIVERY_ALREADY_VERIFIED`;
страница получателя в этом случае должна запросить `GET /api/v1/deliveries/{challengeId}` и показать «доставка подтверждена» (`state = CONSUMED`).

## Действия поддержки (SP11-01)
Роль `SUPPORT` может: записывать инциденты (`INCIDENT_RECORD`), приостанавливать и возвращать водителей (`DRIVER_SUSPEND`, маршруты
`/api/v1/admin/drivers/{userId}/suspend` и `/lift-suspension`), помечать подозрительную активность (`ACTIVITY_FLAG`, `/api/v1/admin/suspicious-activity`) и снимать
блокировку проверки доставки (`INCIDENT_RECORD`). Каждое действие требует код причины и пишет строку аудита с именем администратора. Ни одно из них не ставит
`DELIVERED`, не открывает спор и не меняет вместимость мест и слотов (тест `SupportBoundaryTest`). Пометка подозрительной активности ничего не блокирует,
блокирует только приостановка. Таблица прав ролей зафиксирована тестом `AdminRolePermissionsTest`.

## Замок студента-курьера (SP12-02, RQ-13)
Флаг выключен и включить его нельзя: в коде `CourierFlag.enabled()` всегда `false`; любая попытка задать курьерскую настройку (`jolomo.courier.*`,
`JOLOMO_COURIER_*`, `COURIER_*`) останавливает запуск приложения; в базе `feature_flags` ограничение `student_courier_stays_off` не даёт записать `true`;
в API нет ни маршрута, ни переключателя (тесты `CourierFlagTest`, `CourierLockTest`, `NoClientSwitchTest`, `ModuleBoundariesTest`).
Включить его позже можно только по отдельному меморандуму: изменением кода и новой миграцией, которая снимает ограничение осознанно.

## Завершение брони и метрики (SP07-03)
- `POST /api/v1/bookings/{id}/complete` и `/no-show`: только водитель этой поездки, только из `ACCEPTED` и только когда время отправления наступило
  (до этого 409 `TRIP_NOT_DEPARTED`). По часам, фоновой задачей или пассажиром бронь не завершается; не отмеченная водителем бронь остаётся `ACCEPTED`.
- `NO_SHOW` отдельное состояние. Исход финальный (из `COMPLETED` в `NO_SHOW` и обратно нельзя), повтор того же безопасен. Места не возвращаются, контакты закрыты.
- Полная таблица переходов и определения метрик с числителем и знаменателем: `docs/booking-lifecycle-and-metrics.md` (проверяются тестами).
- Для фронтенда: водитель после отправления видит у принятых броней кнопки «Поехал» и «Не приехал»; обе вызывают маршруты выше.

## Метрики пилота и ночная выгрузка (SP12-01)
- Реестр событий (`EventRegistry`), семь метрик с явными числителями и знаменателями (`MetricsService`) и ночная выгрузка (`ExportService`, `ExportJob`). Определения, когорты и правила псевдонимизации: `docs/pilot-metrics-and-export.md`.
- Если знаменатель метрики равен нулю, она не определена (`null`), а не 0 % и не 100 %.
- Выгрузка **выключена по умолчанию**. Включение: `export EXPORT_ENABLED=true`, `export EXPORT_PSEUDONYM_KEY=$(openssl rand -hex 32)` (и при желании `EXPORT_DIR`). Каждую ночь в 02:30 по Asia/Bishkek пишется `jolomo-export-ГГГГ-ММ-ДД.json` за вчерашние сутки.
- В выгрузке нет телефонов, кодов и документов: идентификаторы заменены псевдонимами, из payload берётся только белый список полей, незарегистрированные события не выгружаются. Ключ хранить в копиях ключей.
- HTTP-маршрутов у метрик и выгрузки нет: файл забирает владелец с хоста.

## Версия уведомления, legal hold, удаление синтетики (SP04-03)

Подробно: `docs/privacy-notice-and-synthetic-purge.md`.

- Версия уведомления хранится у пользователя (`users.notice_version`), реестр версий `privacy_notices`. Маршруты:
  `GET /api/v1/privacy-notice/current`, `GET` и `POST /api/v1/me/privacy-notice`. Изменение версии пишет аудит. Рабочая версия
  `WORKING-1` это заготовка, подписанную версию юриста публикует владелец через `PrivacyNoticeService.publish`.
- Legal hold: `POST` и `GET /api/v1/admin/legal-holds`, `POST .../{id}/release`. Право `LEGAL_HOLD` только у владельца.
- Ночное задание (03:10 Asia/Bishkek) удаляет **только просроченных синтетических** пользователей и всё, что к ним относится,
  пропускает legal hold и связи с людьми вне удаляемой группы, пишет аудит. Реальных людей не трогает: их сроки пусты до юриста.
  Выключатель: `PRIVACY_PURGE_ENABLED=false`.
